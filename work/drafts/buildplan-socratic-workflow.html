Build plan: the Socratic workflow

A reader can tell what gets built in what order, how each step proves it works before the next begins, and what a commit has to show before it is allowed in.

This is the build plan for the blueprint of the Socratic workflow: six phases, each with its subtasks, one binary test gate, and the commit and push that close it. It is written to the brief you get in week 4, as a worked example of the document — and of its discipline: nothing is built that the blueprint does not name, and nothing is pushed that its gate has not passed.

The runs set the order. The week-1 documents are waiting to be scored now, so the scorer and the questioner come before the coherence checker, which has nothing to check until a second document exists. Each phase is dated to the run it must precede.

2 · The rules every phase follows

  • One commit per phase, on main, pushed straight to the remote when the gate has passed. No branches and no pull requests: the gate is the review. The commit message says why the phase is shaped as it is; the gate's transcript — the command, its output, the exit code — goes in the pipeline log, and the message names the entry.
  • A phase begins only after the previous phase's push has succeeded. A push that is rejected, or a gate that fails, stops the clock; the next phase does not start on a promise.
  • A gate is a command with an exit code, run against fixtures that are not student work. A gate a person has to interpret is not a gate.
  • Model steps are gated on shape, and read by a person for sense. A script checks that a score has its headings and its provenance line; an owner reads the score of the fixture and logs what they think of it. Both happen before merge; only the first blocks it.
  • Nothing from the intake folder ever appears in a diff. Before every push: git diff --cached --name-only is read for a team folder, a roster, or an inbox file. The intake root is outside the repository, so this should be impossible; the check is for the day it is not.
  • Every phase leaves the previous one working. The manual path — a lecturer scoring by hand with the sheet, in twenty minutes — is the fallback for any week a phase is late. A missed phase costs an hour; it never costs a team its questions.
  • CI runs what CI can: the link check on every push that touches the repository's documents. Model calls are not run in CI, because the key is course-owned and the fixtures are enough; their transcript lives in the pipeline log instead.

3 · The order, as a graph

Top to bottom is time. A phase begins only when the previous phase's gate has passed and its commit has been pushed. Inside a phase, boxes on one row run in sequence and rows stacked on each other run in parallel — each row is one agent's lane. The yellow boxes are the gate scripts, written in their own lane by an agent that did not write the code they test.

4 · What several agents can build at once

The file contracts in the blueprint's §6 are the seams. Anything on one side of a contract can be written without seeing the other side, so it can be written by a different agent at the same time. Four rules keep that from turning into a merge conflict:

  • Phases are never parallel. No agent starts phase N+1 before phase N's push has succeeded. The gate is the only thing that lets time move.
  • One file, one agent. Lanes are cut along file boundaries, or along functions with a stated signature inside run_documents.py. Two agents never hold the same file open.
  • The gate script is written by someone else. The agent that writes the code does not write the test of it. The gate lane starts from the blueprint's contract, not from the code.
  • Assembly is one lane. Where a step joins the others' work — the instruction assembly in phases 2, 3 and 4 — one agent owns it and starts when the parts it joins exist.

Phase 0 · Ground

Builds blueprint §5 (where things live) and §7 (tests) · before phase 1 · half a day

Nothing that talks to a model. The folder layout the whole design rests on, and the fixtures every later gate runs against.

  1. Lay out the intake folder as blueprint §5 draws it: rubric/, inbox/, teams/, roster.tsv, log.tsv. Move the existing week-01/inbox/ files into inbox/; delete the derived week-01/text/.
  2. Rewrite the intake folder's README.md to describe the per-team layout and the one command a week.
  3. Write roster.tsv for the cohort: team number, first names, Teams channel. On the disk only.
  4. Name the fixtures in project-documentation/test-fixtures/README.md: the gate's PRD as the PRD fixture, the blueprint as the blueprint fixture, and the departure in the blueprint's §9 as the coherence finding the checker must produce.
  5. Make a scratch intake root under the fixtures' own folder structure, so every gate can run against a throw-away copy.

Gate 0. ls -R of the intake root matches the tree in blueprint §5 line for line, with teams/ empty. roster.tsv has one line per team and no line with an empty channel. The fixtures README names three fixtures and where each is used.

Run. One commit: two files in the diff, both documentation. Gate 0's listing goes in the pipeline log. Push; phase 1 starts when the push has landed.

Phase 1 · Intake

Builds blueprint §3 part 2, §4 step 1, §6 manifest.tsv and documents.tsv · before the week-1 run · one day

intake.py becomes step 1 of run_documents.py. Everything here is a script; every subtask has a right answer.

  1. The skeleton of run_documents.py: --week, --root, --team, --step; the step loop; exit codes 0, 1 and 2 as blueprint §7 defines them.
  2. The deliverable guess beside the team guess: prd, blueprint, knowledge, buildplan, eval, decisions, with the Dutch spellings students actually use. Both guesses go in the manifest; both are the lecturer's to correct.
  3. The move: hash before, move, hash after, or stop and say so. -vN when the target exists. A line in log.tsv, a line updated in documents.tsv.
  4. Conversion from the team folder, since the inbox is emptied; the regeneration of a text/ folder goes.
  5. A file with no team or no deliverable stays where it is, with its manifest line, and the run says so and exits 1.

Gate 1. Five files in a scratch inbox: Team 3 PRD.pdf, t05_prd.docx, prd-final.pdf (no team), team-03-prd-v2.md, and a PDF that is not a PDF. After one run: two moved and converted, one is -v2, one stays in the inbox with an empty team cell, one is named as unconvertible, exit 1. After a second run with the manifest corrected: the stray is filed, exit 0, and documents.tsv and log.tsv gain exactly one line each. A third run changes nothing.

Run. One commit, with the three transcripts in the pipeline log. intake.py is removed in the same commit, so there is one door and not two. Push; phase 2 starts when it has landed.

Phase 2 · Scorer

Builds blueprint §3 part 3, §4 step 2, §6 score-<id>.md, §7 instruction assembly · before the week-1 run · one day

The first model call. Its instruction is built from files at run time and nothing else; a script wraps it in a provenance header and checks its shape before anything is written.

  1. The criteria page as text: site/<id>-criteria.html through the extractor agent.py already has.
  2. Instruction assembly: the sheet from rubric/<id>-scoresheet.md verbatim, then the criteria, then the document, then the previous score for the same deliverable if documents.tsv shows one.
  3. The provenance header: the criteria page's last commit, the sheet's content hash, the date.
  4. The call, per document, with the retry rule from run_week.py; written only when ## RETURNED, or ## SCORESHEET and ## BEFORE V1, are present.
  5. No sheet, no score: a deliverable without a sheet or a criteria page is reported by name, and the step continues with the next.
  6. Skip when owners/score-<id>.md exists.

Gate 2. The PRD fixture scores: the file starts with the provenance header and carries the required headings, checked by script. A second run skips it and the file's hash is unchanged. A blueprint fixture with no sheet in rubric/ yields the line unscored: no sheet for blueprint and exit 1, and nothing is written for it. Read by a person, without blocking merge: both owners read the fixture's score and log in the pilot log whether they would sign it; two runs on the same fixture are compared for variance.

Run. One commit. The pipeline log records the provenance header and the headings found — not the score itself, which carries the sheet's bands, and the log is in the public repository. Push; phase 3 starts when it has landed.

Phase 3 · Questioner, register, lint

Builds blueprint §3 parts 5 and 6, §4 step 3, §6 register.tsv, questions.md, message.md, and the two-column contract · before the week-1 run · two days

The part that produces the only file that leaves the building, and the two scripts that stand between it and the door.

  1. register.tsv: read, filter to open · partly · ducked, append, rewrite. The status vocabulary is closed; anything else is a parse error.
  2. The two-column extraction, as a script: parse the score's table, keep weakest evidence and what would raise it by one, drop the score column, the total and the band before the text reaches any prompt.
  3. The questioner's instructions: instructions.txt keeps its rules on history, on questions only, on never quoting a sentence the team did not write — and loses the fetch, since the document is handed in as text. Two files, one for a page and one for a document, or one file with the fetch paragraph made conditional; either way the rules are stated once.
  4. Instruction assembly in the order blueprint §6 fixes: register, this week's text, the columns, the instructions. Cold start: an empty register is passed as such, and the history rules are told they do not yet apply.
  5. Output parsing into register updates, questions.md, and message.md with the fixed opening and closing from a file in the repository.
  6. The lint: criterion codes, /60, band names, the word score. A hit fails the step with the line quoted.

Gate 3. On the PRD fixture's score: questions.md has three to five lines and each ends in a question mark; message.md passes lint; the register gains that many lines, all open. A message with A3 and /60 planted in it fails lint and the run exits 1. On a second fixture with one register question answered in a doctored copy: that question's status becomes answered with a quote, and it is not asked again. A fake roster with distinctive names: none of them appears in any assembled prompt, checked by grep.

Run. One commit, with the four transcripts and the fixture's message.md in full in the pipeline log — it is the one output that is meant to be read. Push. Then the week-1 run, for real: the cohort's PRDs, one command, the exit code and the terminal summary logged, every message.md read by an owner before it is sent.

Phase 4 · Coherence

Builds blueprint §3 part 4, §4 step 2b, §6 coherence.md, and the findings-to-questioner input · before the week-2 run · one day, plus the sheet

The first step that reads more than one document. It has nothing to do until the blueprints arrive, and everything to do then.

  1. The latest version of every deliverable from documents.tsv; the step skips, saying why, when there is only one.
  2. rubric/coherence-scoresheet.md, written by the AEL owner from the rows in the pipeline design note: the questions in both directions, the findings each produces, the 0–3 per direction, the instruction block. Outside the repository, like every sheet.
  3. What the sheet checks, published: a short section on the blueprint criteria page saying a team's documents are read against each other, and how. Before the hand-in, like every criterion.
  4. Instruction assembly and the call; written only with ## TRACE and ## FINDINGS present.
  5. The findings section handed to the questioner beside the two columns, and the questioner's instructions told what a coherence finding is and that both sides are quoted.

Gate 4. On the fixture pair — the gate's PRD and the workflow blueprint — coherence.md has both headings; ## TRACE has one row per line of the PRD's "what it must let a user do" table; ## FINDINGS names the planted departure, checked by grep for the inbox door against the PRD's pull-only rule. With the blueprint fixture removed, the step skips with a named reason and exit 0. The questioner, run after it, produces at least one question tagged coherence in the register.

Run. One commit, with the transcript and the ## FINDINGS of the fixture pair in the pipeline log — our own documents, so publishable. Push. Then the week-2 run.

Phase 5 · Handover and hardening

Builds blueprint §7 (failure, secrets), §10, §11 · before the week-3 run · one day, spread over the week

What turns a script one person can run into a workflow two people can run, and closes the blueprint's open questions that a build can close.

  1. The runbook in the intake folder's README: the Saturday-morning sequence in ten lines, including what to do when the exit code is 1 and when it is 2.
  2. The second owner: the intake root reachable from a second machine, inside the institution's tenant, and --root pointing at it. Which store is a decision (ADR-0013 route 4 names the candidates), and it is taken and written down here.
  3. The invariant-failure policy — return at once or hold for the lecturer — decided on the first real case and written into the sheet's instruction block.
  4. Two decision-log entries: the runtime chosen in blueprint §7, and the inbox door in blueprint §9. Without them the blueprint's own open question stands.
  5. The pilot log for the document pipeline: every fixture run and every live run, one line each, as the page gate keeps.

Gate 5. The second owner runs gates 1 to 4 on their own machine from the runbook alone, without asking a question, and every one passes. The two decision-log entries exist. The runbook's exit-code table matches the code.

Run. One commit, and the pipeline log lists what the second owner had to ask, if anything, and what changed in the runbook because of it. Push.

Where this comes from, and how it is judged

Every phase names the section of the blueprint it builds, and the blueprint names the section of the PRD it implements — which is exactly the chain the coherence checker in phase 4 reads a team's documents for. This build plan will be read against the criteria for the week-4 build plan, published before that hand-in; until then it is a draft in the repository's work/drafts/ folder, beside the blueprint.

Blueprint: the Socratic workflow

A reader can tell what each part does, what passes between the parts, and where the line is that nothing may cross.

This is the teaching team's own blueprint for the pipeline that turns a team's weekly hand-in into a set of Socratic questions. It is written to the same brief you get in week 2, on the same one-to-three-page bar, and it will be read against the same criteria — so it is a worked example of the document, and of the discipline: it implements a PRD, it traces every part back to that PRD, and it says out loud where it departs from it.

Draft, and honest about it. One part of this is built (the intake step); the rest is designed. Where a decision is not yet taken it is in the open questions with a role and a route, which is worth more than a filled section that asserts.

2 · What it builds, in one paragraph

Each week an AEL team posts one document in its Teams channel — a PRD, then a blueprint, then a knowledge architecture, a build plan, and two evaluations. A lecturer drops the file in an inbox. From there the system does four things without further hands: it files the document under the team and the week and turns it into plain text; it scores the document against criteria the team has already read, for the owners only; from week 2 it checks whether this week's document agrees with the ones before it; and it writes three to five Socratic questions for the team, knowing which earlier questions are still open. The lecturer reads the questions and sends them. The team never touches the system, and the system never touches anything but the team's own writing.

The boundary, stated once. Two roots, and nothing crosses between them by accident. The repository is public: it holds the code, the criteria pages and this blueprint. The intake folder is one lecturer's disk: it holds every student document, every score, every question ever asked, and the one file that links a team number to first names. Student work never enters the repository, and nothing that would be damaging in a student's hands ever enters the site.

4 · The flow of one week

One command a week, with the week number as its only argument. Each step runs wherever its input exists and its output does not, so a run that stops can simply be started again and picks up where it broke — the presence of a file is the signal from one step to the next, and there is no queue, no status and no clock to keep anywhere else.

inbox/                              ─ lecturer drops the week's files
   │
   ▼  step 1  intake        (per file)      → teams/team-NN/week-NN/…-original.pdf, …txt
   │
   ▼  step 2  scorer        (per document)  → owners/score-<id>.md
   │
   ▼  step 2b coherence     (per team, from week 2)  → owners/coherence.md
   │
   ▼  step 3  questioner    (per team)      → register.tsv · team/questions.md · team/message.md
   │
   ▼  lint    message       (per team)      → pass, or the run stops here
   │
   ▼  lecturer sends team/message.md — and nothing else
  1. A file with no recognisable team or deliverable goes nowhere. It stays in the inbox with a line in the manifest for the lecturer to fill in. The system never guesses either from what the document says.
  2. A document with no scoresheet is reported, not scored. The scorer does not improvise criteria; unscored: no sheet for blueprint is the whole output, and next week's fix is to write the sheet.
  3. The questioner runs last, and only once every score due this week exists. Its questions are shaped by what the scorer found, which is the design — but it is handed the findings, never the numbers (§6).
  4. A second hand-in of the same document in the same week is a new version, -v2, never an overwrite. Later steps take the highest.

6 · Contracts — what passes between the parts

Every handover is a file with a fixed shape. That is what lets a script check a step's output and what lets a person read it a year later.

FileWritten byRead byShape
manifest.tsvIntakeThe lecturer, then intake againOne line per inbox file: team, deliverable, source, text, word count. Empty cells are the lecturer's to fill.
documents.tsvIntakeCoherence checker, questionerOne line per deliverable id: week, version, path of the current text.
owners/score-<id>.mdScorerOwners; questioner (two columns only); next run of the scorer for the same documentA provenance header — criteria page commit, scoresheet hash, date — then the three invariants as pass or fail, then the sheet, the total and the band, then the three items to revise first. Nothing is returned: a failed invariant is a warning here and a plain note to the team.
owners/coherence.mdCoherence checkerOwners; questioner (findings only)## TRACE: one row per PRD requirement and where each later document carries it, or NONE. ## FINDINGS: orphans, contradictions and dropped questions, each with the quotes that disagree.
register.tsvQuestionerQuestioner, owners, the examiner at the interviewid · asked (week) · about (deliverable or coherence) · question · status (open · answered · partly · ducked · withdrawn) · resolved (week) · evidence (the quote that carries the status)
team/questions.mdQuestionerLecturerThree to five questions, nothing else.
team/message.mdQuestionerLint, then the lecturer, then the teamThe fixed opening the team always gets, the questions, the fixed closing. Fails lint on any criterion code, total, band or the word score.

The contract that matters most is an input, not a file. The questioner is given, from each score written this week, two columns and no more: the weakest evidence quoted and what would raise it by one; and from the coherence report, the findings. It is never given a score, a total, a band, or the sheet. Its questions are shaped by the rubric — that is the design — but a part that never sees a number cannot leak one, and that is a property of the wiring rather than a rule the model has to remember.

Size and costTen teams, at most two scores, one coherence check and one questioner call each: about forty calls a week, none larger than a handful of one-to-three-page documentsA rounding error against the funded line, and small enough to re-run in full when a sheet changes
Secrets and namesThe key in .env beside the script, git-ignored; the roster on the disk it was written on. Neither is read by any part that talks to a modelThe repository is public, and a key committed is a key published

8 · What the wiring enforces

Rules that hold because of how the parts are joined, whoever is running it. Each is a rule the PRD states; the blueprint's job is to make it structural.

  • Numbers never reach the questioner — it is handed columns, not sheets (§6). And the lint behind it fails the run rather than warning.
  • Names never reach a prompt — teams are numbers in every path, file and report. The roster is the only file that knows otherwise, and no part reads it.
  • Student work never enters the repository — the intake root is a sibling folder of the repository.
  • Two audiences, two folders — a file is in owners/ or in team/, and a folder boundary is harder to cross by accident than a file suffix.
  • Every score says what scored it — the criteria page's commit and the sheet's hash, so a sheet edited in week 3 cannot silently rescore week 1.
  • No sheet, no score — an unwritten sheet produces a named gap, never an improvised judgement.
  • Originals are immutable — as received, never edited, never overwritten.
  • One run does not repeat itself — a step whose output exists is skipped, so a re-run after a failure cannot double a team's questions.

The AEL documents are files, and there is nothing to pull — so this blueprint adds one door: an inbox a lecturer fills from the team's channel. The student still supplies nothing beyond the post ADR-0013 already asks for. What the PRD's rule protects — that interview material cannot reach a model service by a student's mistake — is kept, but it is now kept by the lecturer choosing what to drop in, rather than by the wiring. That is weaker, and it is said here so that it can be judged.

10 · Not in this blueprint

Sending the message to Teams automatically — a person does it, on purpose, because forwarding the wrong file should take effort. Archiving the register at the end of the run, which the hand-in routes record already says where to do. The instructor dashboard as one screen. The runtime of the page gate, which has its own record. And the content of any scoresheet — this page says where they are and what shape they have, never what is on them.

Where this comes from, and how it is judged

The design behind this page is the pipeline design note, and the PRD it implements is the PRD for the Socratic gate. Both are in the repository, off the site, because the PRD carries the design of a rubric.

This blueprint will be read against the criteria for the week-2 blueprint, which are published before that hand-in, on this site, beside the assignment — the same criteria yours is read against. Until they exist, this page is a draft in the repository's work/drafts/ folder, which is where every page waits before it is fit to be read by students.
